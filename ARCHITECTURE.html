System documentation

How an enquiry moves through the system

Triage Agent classifies, enriches, and routes inbound client enquiries for a professional services firm — replacing a manual triage step that used to take an analyst about eight hours a week. This page traces the actual mechanism: what talks to what, what a request passes through, and what changes state and when.

01

System architecture

Four moving parts and one hard rule: the intake request is synchronous end to end. The browser's POST /api/enquiries doesn't return until classification, routing, and the review-gate decision have all finished and a row is saved — there's no job queue or polling in between.

02

Enquiry lifecycle

Every submission runs through the same four stages. Where it lands afterward — routed, needs review, or failed — depends on two decision points, not one blended score.

03

How routing works

router.route() never calls Claude and never touches Postgres. It's a pure function over two things: the classifier's structured output, and the enquiry's own submitted fields. One example, threaded through both — an enquiry from a manufacturing client, wanting help preparing compliance documentation, filed as "within a month" rather than urgent.

04

Review actions

A reviewer acting on one needs_review enquiry has three options. Each mutates a different, specific set of fields — there's no shared "review" record, just the one enquiry row changing in place.

05

Retry & failure handling

A failed row is a client-facing problem, not a log line — it stays visible in the Queue's Failed tab with the actual error_message (a refusal, a truncated response, or an unreachable API), and a Retry button re-enters the same pipeline from the top of the lifecycle above: classify → route → gate, against the same stored submission, updating the row in place rather than creating a new one. There's no separate recovery code path — retry is the ordinary pipeline, just re-run on demand instead of once at submission time.

06

Data model

Two tables, no history tables. Corrections overwrite fields in place — was_corrected and reviewed_by record that and by whom a row changed, not a full before/after log.

07

Model selection

MODEL_ID is a plain config value — swapping the classification model needs no code change. Whether a cheaper model is actually safe to swap in isn't a guess, though: it's answered by running the same eval harness (backend/evals/run_eval.py against golden.jsonl) with MODEL_ID overridden, and comparing both accuracy and how trustworthy the confidence score stays.
